#### 二、 数据模拟引擎优化 (产量与损耗对齐)

为了支撑“生产计划达成看板”的业务逻辑，仿真引擎 `simulate_real_cnc_data.py` 需进行以下数据对齐调整：

1. **日计划目标锁定**：
   - 系统需设定静态“日总计划产量”每台设备的标准产量加总*8小时。
   - **达成率计算**：$Achievement = \sum{actual\_output} / Target$。
2. **损耗（次品）仿真关联**：
   - **计算公式**：`defects = input_qty - actual_output`。
   - **逻辑优化**：次品率（$Q$ 的损耗项）必须与设备所属的 **生命周期组 (Group)** 强相关。高风险组（Group 4/5）的 `defect_rate` 波动区间需从原有的随机值修正为固定高阈值（如 6%-15%），确保大屏上“损耗件数”随着设备老化同步上升。

#### 3. V1.4.0 核心修复与逻辑对齐总结

在 V1.4.0 版本的迭代过程中，为了确保仪表盘、事件中心及设备监控等模块的视觉表现与底层物理数据的严谨性，我们进行了以下核心架构级修复与对齐：

1. **实时数据流时间补偿与产量雪崩修复 (`yield_buffer`)**：
   - 修复了 `run_realtime_stream.py` 在 3 秒步长下把每条记录按一整小时满载计算而导致单日产量爆炸（数百万件）的严重 BUG。
   - 引入了 `yield_buffer` 脉冲累加器机制，精准分割真实物理时间份额（约 0.05 分钟），只有当产能碎片累积超过 1.0 时才抛出 1 件成品，确保了三秒高频采集下的平滑稳定输出。

2. **多终端时区聚合与时间轴错乱根治**：
   - 修复了因为 SQLite/PostgreSQL `TruncHour` 函数处理时区偏差导致的图表渲染错位（如将 10h/11h 的产量挤占到 9h 柱状图上）。
   - 统一改用纯 Python 内存级 `localtime()` 提取小时特征，并将后端返回的数据严格钉死在早晨 **8:00 (8h)** 作为原点，实现了前后端数据槽位的绝对对齐。

3. **双擎统一的极值与基线触发修正**：
   - 回调了进给速度 (`feed_velocity`) 生成的统计基线至正常的 20 mm/s，消除了原先由于均值过小而持续触发 `LOW_VELOCITY`（进给极低）假报警的现象。
   - 新增**人工异常尖峰注入逻辑**，以一定的概率均衡注入针对主轴电流 (`HIGH_CURRENT`) 和主轴功率 (`HIGH_POWER`) 的极限超出数据，确保三类物理报警在「系统异常事件统计」中分布均匀。

4. **单机 OEE 精确计算重构 (防溢出)**：
   - 废弃了使用固定时间窗口的单机表现度 ($P$) 估算，改为动态抓取设备当日首尾记录 `$first_rec$` 与 `$latest_rec$` 算得精确时间偏差 $\Delta T$。
   - 通过强制判断 $P = \min(\frac{产出}{标准产能 \times \Delta T}, 1.0)$，彻底根除了个别设备 OEE 飙升突破 150%、或闲置设备出现 `--` 零值异常的情况。

5. **UI 与用户跳转链路深度抛光**：
   - Dashboard 与 Event 界面中「报警频率趋势图」的时段彻底拉齐（完全同步获取 `api_alert_trend` 取过去 24h/1h间隔的数据格式）。
   - **跳转联动联动**：Dashboard「实时异常上报」增加全局脚部总量统计（如 “共 42 条报警”），点击直接跳转 `/devices/?device={ID}` 并将设备名反推输入到搜索框中，实现设备精准快筛。
   - 优化了各项视觉留白与层叠级问题：放宽 OEE 良品/次品双卡间距、下移 Echarts `markPoint` 峰值文字防止遮挡、拉长事件中心的长条图容器高度缓解视觉黏结。
