## 修复记录 #002 — 项目启动卡死（Critical）

- **发生时间**：2026-02-26（周四）16:09
- **修复完成**：2026-02-26（周四）16:18
- **操作者**：Antigravity（AI 辅助 DevOps）

### 问题描述

执行 `python manage.py runserver` 或 `python manage.py check` 后，进程永久挂起，无任何输出，只能通过 Ctrl+C 强制终止。

### 诊断过程

**Step 2 — 追踪 Ctrl-C 堆栈**

Ctrl+C 终止后，堆栈指向：

```
monitor/views.py line 83:
    _LR_MODEL, _SCALER, _FEAT_NAMES = _load_artifacts()

            → import sklearn
                → from sklearn.base import clone
```

**Step 3 — 隔离验证**

**venv 中的 `pandas`（及依赖的 `numpy`、`scikit-learn`）二进制包（`.so` / `.dylib`）损坏**，疑因 macOS 文件同步（iCloud / AirDrop）在传输大型 C 扩展库时造成字节级损坏。`pandas` 在初始化 C 层时触发死锁，导致整个 Python 进程挂起。

## 预防建议

1. **不要将 `venv/` 纳入 iCloud Drive / Dropbox 同步**：大型 C 扩展库在同步过程中极易损坏。建议在 `.gitignore` 基础上，同时对 iCloud 设置排除规则。

2. **使用系统 Python 创建 venv**：避免使用通过 MAS（Mac App Store）安装的 Python 版本，优先使用 `python.org` 官方安装包。

3. **models 加载建议用懒加载**：`views.py` 顶层的 `_load_artifacts()` 调用，可考虑改为首次请求时才执行，降低启动时的依赖风险：

   ```python
   # 当前方案（模块顶层，启动时执行）
   _LR_MODEL, _SCALER, _FEAT_NAMES = _load_artifacts()
   
   # 推荐方案（懒加载，首次推断时执行）
   _LR_MODEL = _SCALER = _FEAT_NAMES = None
   _artifacts_loaded = False
   
   def _ensure_artifacts():
       global _LR_MODEL, _SCALER, _FEAT_NAMES, _artifacts_loaded
       if not _artifacts_loaded:
           _LR_MODEL, _SCALER, _FEAT_NAMES = _load_artifacts()
           _artifacts_loaded = True
   ```

## 修复记录 #003 — 生产计划达成看板「今日产量」锁死在 268,800

- **发生时间**：2026-03-04（周三）23:14
- **修复完成**：2026-03-04（周三）23:47
- **操作者**：Antigravity（AI 辅助 DevOps）
- **严重程度**：🔴 高（产量数值不刷新，严重影响演示可信度）

### 问题描述

仪表盘左侧「生产计划达成看板」卡片中：

- **今日总产量** 始终固定显示 **268,800 件**，每 3 秒一次的轮询后数值不变
- 进度条 100%，达成率 100.0%
- 良品数同样固定为 268,800，次品数固定为 40,030

用户已实现实时仿真引擎（每 3 秒写入数据），预期产量应随时间不断递增且由于次品率的存在不应超过目标产量，但实际上产量被硬锁。

### 根本原因（三层叠加 Bug）

#### Bug 1：历史批量数据污染今日统计（`views.py`）

`simulate_real_cnc_data.py` 设置 `DAYS=7`，生成过去 7 天的历史数据。由于今天属于这"过去 7 天"的最后一天，数据库中存在大量 `timestamp` 落在今天的历史记录：

```python
# simulate_real_cnc_data.py
DAYS = 7
start_time = now - timedelta(days=DAYS)   # 7天前到现在，包含今天
```

而 `api_dashboard_stats` 使用「今日本地零点」作为查询起始：

```python
# views.py (修复前)
start_of_local_day = local_now.replace(hour=0, minute=0, second=0, microsecond=0)
today_all_qs = ProductionSensorData.objects.filter(timestamp__gte=start_of_local_day)
```

这导致今天的历史预播种数据被一并统计进来，产出量（`total_output`）远大于目标产量（`daily_target`）。

**量化估算**：25 台全 Running 设备 × (1000+800+2000 件/h) ÷ 4 ≈ 全天 7 天历史中今天一天的理论产量 ≈ 数十万件，远超 `daily_target=224,000`。

#### Bug 2：实时写入在同一天继续叠加

实时引擎每 3 秒写入 25 条记录，时间戳为 `timezone.now()`，同样落在「今日零点之后」，与历史数据混在一起，进一步累加 `total_output`。

#### Bug 3：前端硬上限 cap 将产量锁死（`dashboard.html`）

由于 `total_output >> daily_target`，前端的限流逻辑将产量等比例压缩至 `TARGET * 1.2`：

```javascript
// dashboard.html (修复前)
if (TARGET > 0 && actual > TARGET * 1.2) {
    const scale = (TARGET * 1.2) / actual;
    actual = Math.round(actual * scale);   // ← 固定为 TARGET * 1.2
    input = Math.round(input * scale);
}
```

`daily_target = 28,000 件/h × 8h = 224,000`，`TARGET * 1.2 = 268,800`。

由于后端每次都返回远超上限的值，前端等比例 scale 后产量**每次都精确等于 268,800**，数值无法变动。

### 修复动作

#### 修复 1：后端改为仅统计最近 2 小时实时数据

```python
# views.py (修复后)  — V1.4.1
realtime_window_start = local_now - timedelta(hours=2)
today_all_qs = ProductionSensorData.objects.filter(
    timestamp__gte=realtime_window_start
)
```

**设计依据**：
- 实时引擎每 3 秒写入 25 条，2 小时内 ≈ 60,000 条实时数据
- 历史批量数据 `timestamp` 均为系统重置前的过去时间，不会落入"最近 2 小时"
- 2 小时窗口足以展示一个完整实时班次会话的产量积累趋势

#### 修复 2：前端移除硬上限 cap 逻辑

```javascript
// dashboard.html (修复后)  — V1.4.1
// 移除整个 if (actual > TARGET * 1.2) {} 块
const actual = d.total_output || 0;
const input = d.total_input || 0;
// 进度条宽度仍通过 rate = Math.min(100, ...) 限制在 100% 以内
const rate = Math.min(100, TARGET > 0 ? (actual / TARGET * 100) : 0);
```

产量数值直接展示真实值，进度条不超过 100%，允许超出目标时显示绿色满条。

### 验证结果

修复后预期行为：
- 实时产量从 0 开始每 3 秒小幅递增（约每步 +25×[0-2] 件）
- 产量随时间线性增长，不会突然跳到某个固定值
- 进度条从 0% 缓慢增长，不会始终 100%
- 次品数 = `total_input - total_output`，由实际次品率决定，不会固定

### 涉及文件

| 文件 | 修改类型 | 说明 |
|------|---------|------|
| `monitor/views.py` | 后端逻辑 | 修改 `today_all_qs` 查询范围为最近 2h（临时措施，V1.4.2 已回滚） |
| `monitor/templates/monitor/dashboard.html` | 前端逻辑 | 移除 `if actual > TARGET*1.2` cap 块 |
| `Document/数据模拟设计文档.md` | 文档更新 | 追加 V1.4.1 修复说明章节 |

## 修复记录 #004 — 产量爆炸至 940 万件（#003 修复引入的新 Bug）

- **发生时间**：2026-03-04（周三）23:21

- **操作者**：Antigravity（AI 辅助 DevOps）
- **严重程度**：🔴 高（修复 #003 过程中引入的副作用，产量反而变得更夸张）

### 问题描述

修复 #003（将查询窗口改为「最近 2 小时」并移除前端 cap）后，产量从 268,800 件反而跳升到约 **940 万件**，比原问题更加夸张。

### 诊断过程

**直接查询数据库**：

```python
# 查询结果：
Total records in DB: 36,130
Total actual_output (all time): 32,414,034   # ← 3200万件！
avg actual_output per record: 897 件/条         # ← 每条3秒记录约产出1000件
Record spacing: 3 seconds                       # ← 间隔正确，每3秒一条
loading_time: 60.0 分钟                         # ← 🐛 关键线索！
```

**根本原因**：`monitor/management/commands/run_realtime_stream.py` 中的 `_gen_running_record` 函数与 `simulate_real_cnc_data.py` 的实现完全不同。管理命令版本使用固定的 `LOADING_TIME=60 分钟` 计算产量：

```python
# run_realtime_stream.py （修复前 - 错误逻辑）
actual_run = max(0.0, LOADING_TIME - downtime)      # 60 分钟！
theoretical_output = (actual_run / 60.0) * cap      # ≈ standard_capacity = 1000
out = max(0, int(theoretical_output * perf_ratio))  # ≈ 980 件/条 ❌
```

每条 3 秒的实时记录却按照 **60 分钟满负荷**来计算产量，因此：
- 每条记录 `actual_output ≈ 980 件`**（应为 0~1 件）**
- 5小时运行 × 3600/3 × 25台 × ~897 = **约 3,220 万件**

### 为什么 #003 的「2小时窗口」修复反而使问题更严重？

#003 移除了前端 `if (actual > TARGET*1.2)` cap 逻辑，让错误的大产量直接透传到前台。`2h 窗口 × 25台 × 2400步 × 897件/步 = 约 1,080 万件`，直接展示出来。

### 修复动作

#### 修复 1：`run_realtime_stream.py` — 引入 V5 脉冲累加器（yield_buffer）

```python
# 修复后 (V1.4.2)
STEP_SECS = float(STREAM_INTERVAL)    # 3.0 秒
STEP_MINS = STEP_SECS / 60.0          # 0.05 分钟

def _gen_running_record(device, ts, group_idx):
    input_fraction = cap / 3600.0 * STEP_SECS      # 每步理论份额 ≈ 0.833 件
    pulse = input_fraction * perf_ratio
    device.yield_buffer += pulse
    if device.yield_buffer >= 1.0:
        produced = int(device.yield_buffer)          # 约每 1.2 秒出 1 件
        device.yield_buffer -= produced
    else:
        produced = 0                                 # 大多数步骤产出=0
    # loading_time 写入实际步长 STEP_MINS=0.05，而非固定 60 分钟
    return ProductionSensorData(..., loading_time=STEP_MINS, ...)
```

同时修正 `_gen_idle_record` 和 `_gen_down_record` 的 `input_qty=0`（之前错误地写入了 `standard_capacity`）。

#### 修复 2：`views.py` — 恢复今日零点查询

`views.py` 的 `today_all_qs` 恢复使用「今日本地零点」统计（V1.4.1 临时改为 2h 窗口已回滚），现在产量数值正确后无需时间窗口隔离。

## 修复记录 #005 — OEE P 崩溃（20.1%）及 yield_buffer 持久化漏洞

- **发生时间**：2026-03-04（周三）23:39
- **修复完成**：2026-03-05（周四）10:22
- **操作者**：Antigravity（AI 辅助 DevOps）
- **严重程度**：🟡 中（功能性 Bug，影响指标准确性，但不阻断演示）

### 问题描述

重启守护进程后出现：
1. **OEE P（性能）从 87% 骤降至 20.1%**
2. **产量再次超出目标**（1,072,227 件）

### 根本原因

#### Bug A：剩余 1,200 条错误记录

首次清理只删除了 `actual_output > 10` 的记录，但守护进程重启后、清理执行前的 1.5 分钟内又生成了 1,200 条旧格式记录（`loading_time=60, actual_output≈900`）。这些记录在清理时因时间窗口错开而幸存。

#### Bug B：`yield_buffer` 持久化漏洞

`run_realtime_stream.py` 主循环：

```python
while True:  # ← 每次迭代
    devices = list(DeviceInfo.objects.all())  # ← 创建全新对象！
    for dev in devices:
        if not hasattr(dev, 'yield_buffer'):
            dev.yield_buffer = 0.0   # ← 每次都初始化为 0
```

每次循环 `list(DeviceInfo.objects.all())` 创建全新 Python 对象，导致 `yield_buffer` 每 3 秒重置一次。结果：

- 每步 `pulse = 0.833`，永远 `< 1.0` → `produced = 0` 恒成立
- 占大多数步骤的产量为 0，偶尔因浮点边界触发 1，导致 `avg_output ≈ 0.18`（预期 0.756）

#### Bug C：OEE P 计算对 `loading_time=0.05` 失真

旧 OEE P 公式：`P = Σactual / Σ(loading_time/60 × cap)`  
当 `loading_time=0.05` 时每条理论产量 ≈ 0.000833，与 `actual=0.18` 相比得出 `P≈216%`。  
而与旧记录（`loading_time=60`，`actual=900`）混合时导致 P 估算失真到 20.1%。

#### Bug D：Idle/Down 记录遗留错误 `input_qty`

`_gen_idle_record` 修复前写入 `input_qty=device.standard_capacity`（≈1000），导致今日总投入虚高至 27,065（应为 ~1,000）。

### 修复动作

| 修复 | 内容 |
|------|------|
| 清理剩余错误数据 | 删除 1,200 条 `loading_time≥50` 的流水 + 241 条报警；修正 13 条 Idle/Down 记录的 `input_qty=0` |
| `run_realtime_stream.py` yield_buffer 持久化 | `devices` 移到 `while` 循环**外**，循环内只调用 `refresh_from_db` 更新状态字段；新增设备变化检测重新加载逻辑 |
| `views.py` OEE P 计算重构 | 改用全局速率公式：`P = 实测速率(件/h) / 理论产能(件/h)`，不再依赖 per-record 的 `loading_time` |

### 最终验证结果（2026-03-05 10:23）

| 指标 | 修复前 | **修复后** |
|------|-------|-----------|
| `avg_output` / 条 | 0.180（yield_buffer 失效）| **0.760**（≈预期 0.756）|
| 今日 `loading_time>=50` 记录 | 1,200 条 | **0 条** |
| 今日产量（自零点）| 1,072,227 件 | **669 件**（正常积累中）|
| 今日投入 = 今日产量 | 否（投入 27,065，产量 1,065）| **是（投入 682 ≈ 产量 669）** |
| OEE P | 20.1% | **~81.4%** |


## 修复记录 #006 — 单设备 OEE 异常溢出与 `--` 渲染修复 (V1.4.3)

- **发生时间**：2026-03-05
- **操作者**：Antigravity (系统架构师 / 数据逻辑专家)
- **严重程度**：🔴 高（影响单设备核心指标呈现与逻辑稳健性）

### [Logic Audit] 问题诊断分析

1. **分母失准与 150% 溢出**：
   在 `views.py` `api_device_matrix` 中，单设备的 OEE 原本是通过读取设备的**最新单条流水记录**提取的。
   考虑到当前系统采用了 3 秒为步长的 `STEP_SECS` 极高频采用，3 秒内的标准产能份额极小（通常在 0.833 件以内），而由于良品只能以整数（脉冲）单位脱离缓冲池出件，一旦当前 3 秒内刚好输出 `1 件`，单条记录的性能 P 就被计算为 `1.0 / 0.833 = 120%` 甚至更高。极高频脉冲与单条记录评估，使得 OEE 面临剧烈的振荡及溢出。
2. **零值崩溃与 `--` 显示**：
   受限于没有动态容错。若一台设备今日暂未产生流水，`latest` 查询为空而直接使得 `oee=None` 传递给前端。前端的渲染脚本亦无针对 `undefined` 或 `null` 回退到 0 的机制，进而直接显示了占位符 `--`。
3. **脉冲余数重置漏洞**：
   在 `run_realtime_stream.py` 下，设备的脉冲余数累加器 `yield_buffer` 仅仅通过 Python 对象属性绑定 `getattr(device, 'yield_buffer')` 暂存。重启生成脚本必定使其丢失，更在每次 `refresh_from_db()` 或其他重新查询逻辑时，随时有被清零的风险。

### [Code Patch: views.py] 动态时间窗口计算

彻底废除单条记录 OEE 计算逻辑。利用针对该设备的今日所有流水记录，实行时间差分推导理论产能：
```python
# == 计算今日动态 OEE ==
today_recs = ProductionSensorData.objects.filter(device=dev, timestamp__gte=today_start).order_by('timestamp')
first_rec = today_recs.first()
if first_rec and latest.timestamp > first_rec.timestamp:
    # 实际运转时长（小时）
    delta_t_hours = (latest.timestamp - first_rec.timestamp).total_seconds() / 3600.0
    if delta_t_hours > 0:
        # 理论最大产量 = 标准产能 * 运转时长
        theo_max = dev.standard_capacity * delta_t_hours
        
        # 汇总今日实际产出与投入
        agg = today_recs.aggregate(s=Sum('actual_output'), i=Sum('input_qty'))
        actual_out = agg['s'] or 0
        input_qty = agg['i'] or 0
        
        # 计算 P 和 Q （A 假定 100% 因为这是单机的全运转时段）
        p_val = min(actual_out / theo_max, 1.0) if theo_max > 0 else 0.0
        q_val = min(actual_out / input_qty, 1.0) if input_qty > 0 else 1.0
        oee_val = round(p_val * q_val, 4)
    else:
        oee_val = 0.0
else:
    oee_val = 0.0
```

### [Code Patch: simulator] 产量脉冲写入限制与持久化

对于仿真脚本作了双重增强防溢出和丢失：
1. 更新数据库表结构 (`migrations/0004_deviceinfo_defect_buffer_deviceinfo_yield_buffer.py`)。直接将 `yield_buffer` 纳入 `DeviceInfo` 的 Model 数据列中持久化。
2. 配置极为严苛的脉冲出件上限 `min(1, int(buffer))`，限制 3 秒内就算堆积也顶多算 1 件产生：
```python
pulse = input_fraction * perf_ratio
device.yield_buffer += pulse

if device.yield_buffer >= 1.0:
    # 物理限制：3秒内产量无论如何堆积，单次输出强限制为不超过1件
    produced = min(1, int(device.yield_buffer))
    device.yield_buffer -= produced
else:
    produced = 0
```
