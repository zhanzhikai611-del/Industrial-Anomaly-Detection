## 修复记录 #001 — venv 冗余副本清理

- **发生时间**：2026-02-26（周四）15:23
- **修复完成**：2026-02-26（周四）15:30
- **操作者**：Antigravity（AI 辅助 DevOps）
- **严重程度**：⚠️ 低（不影响运行，但拖慢 IDE 索引速度）

### 问题描述

项目 `venv/` 目录下出现带 ` 2` 后缀的冗余文件夹：

```
venv/
├── include          ← 正本（含 python3.12/）
├── include 2        ← ❌ macOS 同步冲突空副本
├── lib              ← 正本（含 python3.12/）
├── lib 2            ← ❌ macOS 同步冲突空副本
├── bin/
└── pyvenv.cfg
```

### 根本原因

iCloud Drive / AirDrop 文件同步冲突在 macOS 上产生的「副本」空目录（确认 `include 2` 与 `lib 2` 均为空目录，不含任何文件）。

### 修复动作

```bash
# 1. 对比内容（include 2 / lib 2 均为空目录）
# 2. 安全删除冗余副本
rm -rf "venv/include 2" "venv/lib 2"

# 3. 验证无残留
find venv/ -name "* 2" -o -name "* 2.*"  # 输出为空
```

### 验证结果

```
venv/
├── bin/
├── include/
├── lib/
└── pyvenv.cfg       ← 结构干净
```

## 修复记录 #002 — 项目启动卡死（Critical）

- **发生时间**：2026-02-26（周四）16:09
- **修复完成**：2026-02-26（周四）16:18
- **操作者**：Antigravity（AI 辅助 DevOps）
- **严重程度**：🔴 高（项目完全无法启动）

### 问题描述

执行 `python manage.py runserver` 或 `python manage.py check` 后，进程永久挂起，无任何输出，只能通过 Ctrl+C 强制终止。

### 诊断过程

**Step 1 — 检查 MySQL 服务状态**

```bash
ps aux | grep -i mysql
# → 发现 MySQL 运行在 /usr/local/mysql/bin/mysqld，进程正常
/usr/local/mysql/bin/mysqladmin -u root -pbaby0611 status
# → Uptime: 149  Threads: 2  ← 连接正常
```

> 结论：MySQL 服务正常，连接可达，排除数据库原因。

**Step 2 — 追踪 Ctrl-C 堆栈**

Ctrl+C 终止后，堆栈指向：

```
monitor/views.py line 83:
    _LR_MODEL, _SCALER, _FEAT_NAMES = _load_artifacts()
        → joblib.load('logistic_model.pkl')
            → import sklearn
                → from sklearn.base import clone
                    → import pandas
                        → pandas/__init__.py line 46  ← 卡死点
```

**Step 3 — 隔离验证**

```bash
# 系统 Python 可正常导入 pandas
python3 -c "import pandas; print('ok')"  # → pandas ok ✓

# venv 的 Python 永久挂起
venv/bin/python -c "import pandas; print('ok')"  # → 挂死 ✗
```

### 根本原因

**venv 中的 `pandas`（及依赖的 `numpy`、`scikit-learn`）二进制包（`.so` / `.dylib`）损坏**，疑因 macOS 文件同步（iCloud / AirDrop）在传输大型 C 扩展库时造成字节级损坏。`pandas` 在初始化 C 层时触发死锁，导致整个 Python 进程挂起。

> ⚠️ 注意：`manage.py check` 本身不需要数据库，但它会导入 `monitor.urls → monitor.views`，而 `views.py` 在**模块顶层（第 83 行）**调用了 `joblib.load()` 加载 sklearn 模型，从而触发了损坏的 pandas 导入链。

### 修复方案：重建 venv

```bash
# 1. 删除损坏的旧 venv
rm -rf venv

# 2. 用系统 Python 3.12 重建干净 venv
python3 -m venv venv

# 3. 升级 pip
venv/bin/pip install --upgrade pip

# 4. 安装所有依赖
venv/bin/pip install -r requirements.txt
# 安装成功：
#   Django-6.0.2 / PyMySQL-1.1.2 / numpy-2.4.2
#   pandas-3.0.1 / scikit-learn-1.8.0 / joblib-1.5.3
#   scipy-1.17.1 / threadpoolctl-3.6.0 / django-simpleui-2026.1.13
```

### 验证结果

```bash
# 科学计算库导入测试
venv/bin/python -c "
import pandas as pd, sklearn, numpy as np, joblib
print('✓ pandas', pd.__version__)
print('✓ sklearn', sklearn.__version__)
print('✓ numpy', np.__version__)
"
# ✓ pandas 3.0.1
# ✓ sklearn 1.8.0
# ✓ numpy 2.4.2

# Django 系统检查

# → System check identified no issues (0 silenced). ✅

# 服务器启动

# → Starting development server at http://127.0.0.1:8000/ ✅
```

## 预防建议

1. **不要将 `venv/` 纳入 iCloud Drive / Dropbox 同步**：大型 C 扩展库在同步过程中极易损坏。建议在 `.gitignore` 基础上，同时对 iCloud 设置排除规则。

2. **使用系统 Python 创建 venv**：避免使用通过 MAS（Mac App Store）安装的 Python 版本，优先使用 `python.org` 官方安装包。

3. **models 加载建议用懒加载**：`views.py` 顶层的 `_load_artifacts()` 调用，可考虑改为首次请求时才执行，降低启动时的依赖风险：

   ```python
   # 当前方案（模块顶层，启动时执行）
   _LR_MODEL, _SCALER, _FEAT_NAMES = _load_artifacts()
   
   # 推荐方案（懒加载，首次推断时执行）
   _LR_MODEL = _SCALER = _FEAT_NAMES = None
   _artifacts_loaded = False
   
   def _ensure_artifacts():
       global _LR_MODEL, _SCALER, _FEAT_NAMES, _artifacts_loaded
       if not _artifacts_loaded:
           _LR_MODEL, _SCALER, _FEAT_NAMES = _load_artifacts()
           _artifacts_loaded = True
   ```
