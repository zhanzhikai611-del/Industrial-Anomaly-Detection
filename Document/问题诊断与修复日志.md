- **修复完成**：2026-03-07（周六）02:40
- **操作者**：Antigravity (AI 辅助 DevOps)
- **严重程度**：🔴 高（仪表盘完全无数据，显示为 --）

### 问题描述
仪表盘进入后所有数值显示为 `--`，浏览器控制台报错 `Uncaught SyntaxError: Invalid or unexpected token`。同时用户反馈无法登录（疑为 CSRF 或 Session 问题）。

### 根本原因
1. **JavaScript 语法错误**：在 `dashboard.html` 的 `fetchAlerts` 逻辑中，一段 HTML 字符串拼接在多行显示时未正确处理，导致浏览器解析为非法 Token。

3. **缓存干扰**：Daphne 服务在模板修改后未及时刷新内存中的缓存，导致即便文件已修改，浏览器仍收到旧的错误版本。

### 修复措施
1. **代码回归**：使用 `git restore` 将 `base.html` 和 `dashboard.html` 恢复至最后一个稳定 Committed 状态。
2. **多行字符串修正**：确保 JS 中的 HTML 模板字符串单行显示或使用反引号。
3. **冲突解决**：将 `base.html` 中的选择器统一改为 `window.$ = window.$ || (id => document.getElementById(id))`，确保全局唯一性。
4. **服务重启**：重启 Daphne 进程并清理 `.pyc` 缓存，确保浏览器加载最新模板。
5. **身份验证重置**：手动重置了 `admin` 账号密码为 `admin123` 并通过自动化测试验证了登录与仪表盘数据的完整性。

修复过程中使用了 `Playwright` 自动化诊断脚本（`/tmp/debug_auth_dashboard.py`）。该脚本能模拟「登录 -> 访问仪表盘 -> 捕获控制台错误 -> 截图」的完整链路，帮助快速定位了渲染失效的关键点。

## 修复记录 #012 — 数据流暂停视觉反馈修复与时间戳一致性校正 (V2.1.2)

- **发生时间**：2026-03-08（周日）14:11
- **修复完成**：2026-03-08（周日）14:20
- **操作者**：Antigravity (AI 辅助 DevOps)
- **严重程度**：🟡 中（UI/UX 误导，影响数据一致性觉察）

### 问题描述
在系统设置页面由于手动“暂停数据流”时，后端仿真脚本同步停止写入数据库。然而，前端仪表盘的折线图（实时流水）仍会以每 3 秒一个点的速度向右“生长”，产生后台仍在运行的错觉。

### 诊断结果
1.  **后端接口伪造时间轴**：在 `monitor/views.py` 的 `api_realtime_stream` (对应 `/api/stream/`) 接口中，每次查询无论数据库数据是否更新，都会将记录的时间戳覆盖为 `timezone.now()`。这导致前端始终接收到“新”的时间点。
2.  **前端轮询无状态拦截**：在 `dashboard.html` 中，`pollAll()` 函数为了保证离线加载能力，禁用了对 `is_realtime_active` 开关的检测，导致页面在任何状态下都以固定步长请求。

### 影响范围
- **用户决策**：误导管理员认为数据流依然存续。
- **数据回溯**：在折线图上形成了与数据库物理记录不符的虚假时间横轴，混淆了真实停机时段的起止点。
- **系统资源**：虽然资源消耗极低，但造成了无意义的重复轮询数据传输。

### 修复措施
1.  **后端回归真实数据**：修正 `monitor/views.py` 逻辑，移除 `time.now()` 强行覆盖，接口始终返回数据库中该记录的原始 `timestamp`。
2.  **前端数据排重逻辑**：保留 `dashboard.html` 原有的轮询逻辑以支持“快照展示”，但由于后端时间戳不再变化，前端 JS 仪表逻辑中的 `if (tsArr[last] === newTimestamp) return;` 会自动拦截重复绘制，从而使折线图在暂停瞬间实现“画面定格”的真实视觉反馈。

## 修复记录 #008 — 仪表盘左侧数据消失与 单态 OEE 过低修复 (V2.1.2)

- **发生时间**：2026-03-08（周日）16:23
- **修复完成**：2026-03-08（周日）16:30
- **操作者**：Antigravity (AI 辅助 DevOps)
- **严重程度**：🔴 高 (核心看板数据异常)

### 问题描述
1.  **看板数据消失**：由于 V2.1.1引入「墙钟法」时对 `local_now` 变量进行重构，导致 `api_dashboard_stats` 函数中变量定义冲突，造成 OEE 看板及生产计划达成指标（今日总产量等）完全不显示。
2.  **单机 OEE 过低**：单机 OEE 计算采用 `Now - First_Record`。在项目刚启动或清空数据后的前几分钟，由于 ΔT 时间基数太小，而产量尚未累积，导致 OEE 指标呈现个位数，用户体验较差（由于分母极小而产量为零）。

### 诊断过程
- **看板修复**：追踪 `monitor/views.py` 报错堆栈，发现 `local_now` 未在使用前定义，且 `today_start` 的逻辑被错误注释。
- **OEE 优化**：分析单机 OEE 公式，发现在 $T < 10min$ 时，$Theo_{Max} = Cap \times \Delta T$ 的分母过于敏感。

### 修复动作
1.  **修复变量引用**：在 `api_dashboard_stats` 顶部恢复 `local_now` 与 `today_start` 的正确初始化。
2.  **设置时间补偿底限**：在 `api_device_matrix` 中引入 `max(delta_t_hours, 10/60.0)`。即无论启动多久，前 10 分钟均按 10 分钟作为基准分母，避免启动瞬间的“百分比崩塌”。

### 验证结果
1.  **看板恢复**：仪表盘左侧 OEE 三分图及产量图表重新显示正确数据。
2.  **OEE 复归正常**：单机 OEE 在启动初期不再显示为 1%~5%，而是平滑过渡，真实反映当前产能水平。

在 V3.0 HTMX SPA 架构下，当用户从仪表盘/设置页切换至「账号管理」页时，屏幕会被灰黑色半透明蒙版完全遮盖。

### 根本原因 (Race Condition & OOB Initialization)

这是一个典型的 SPA 渲染竞态条件问题：

3.  **OOB 区域异步初始化缺位**：模态框位于 `#global-modals-area` (OOB)，原有的 HTMX 监听器只初始化了主内容 target，导致该区域的 Alpine 组件处于未激活状态。

### 修复动作

1.  **全局核心防御**：在 `base.html` 注入全局 `[x-cloak] { display: none !important; }`，确保所有弹窗在 JS 运行前绝对不可见。
2.  **增强 HTMX 桥接逻辑**：重写 `base.html` 的监听器，引入对 `#global-modals-area` 的自动探测与二次初始化，并增加 50ms 缓冲。
3.  **样式层级清理**：彻底剔除 `account.html` 中的内联样式，统一由 `account.css` 驱动。

### 验证结果

- 多页频繁切入 Account 页，蒙版不再闪现，布局及初始化完美。

## 修复记录 #012-B — SPA 模式下 OOB 模态框泄露/无法关闭 (Critical Bug)

- **发生时间**：2026-03-16（周一）20:51
- **修复完成**：2026-03-16（周一）21:05
- **操作者**：Antigravity
- **严重程度**：🔴 高（导致 UI 锁定，无法正常操作）

### 问题描述

在 V3.0 SPA 虚拟路由架构下，快速点击“系统设置”或连续点击导航栏，会导致“立即重置风险分布”确认弹窗意外弹出。且该弹窗无法通过点击关闭按钮或蒙版关闭，整个背景变黑（双重阴影），只能通过刷新浏览器恢复。

### 根本原因

1.  **OOB 事件积压**：原本 `setting.html` 将模态框放在 `hx-swap-oob="true"` 区域。在 SPA 模式下，每次切换页面都会通过 OOB 强制替换全局 `#global-modals-area`。
2.  **Alpine 监听器残留**：由于 HTMX 的 OOB 替换是物理销毁 DOM 节点，Alpine.js 挂载在 `window` 上的自定义事件监听器（`@open-reset-modal.window`）在节点被 HTMX 剔除时未能及时自动解绑。
3.  **幽灵实例**：连续点击时，内存中积攒了多个属于已销毁 DOM 的 Alpine 逻辑实例。当事件流紊乱时，弹窗被“幽灵”实例误触发，而关闭按钮绑定的却是当前活跃 DOM 的逻辑，导致关闭失效。

### 修复动作

1.  **回归内容块管理**：将 `setting.html` 和 `account.html` 中的页面级模态框从 `extra_body` (OOB) 移回 `content` 块。
2.  **生命周期同步**：模态框现在跟随 `#main-content` 整体进行 `innerHTML` 替换。HTMX 在替换 `main-content` 时会完全重置该区域的 DOM 环境，Alpine 也会随之正确销毁和重建监听器及状态。
3.  **消除 OOB 依赖**：仅保留全局性的 Toast 逻辑在 OOB 中，页面特定的确认框彻底回归所属页面。


### 验证结果 (V3.1.0)

- **测试 1**：在侧边栏连续疯狂点击“系统设置” → ✅ 弹窗严格静默，不再被误触。
- **测试 2**：从设置页跳转到账号页 → ✅ 设置页的重置弹窗 DOM 被彻底物理清除，不再残留。
- **测试 3**：账号页双击 → ✅ 下方分页器正常，黑色方块（Toast 残留）彻底消失。

### 经验教训
在 HTMX + Django 的 SPA 架构中，如果使用了 OOB (Out-of-Band) 技术挂载模态框，**必须在 `partial.html` 中显式包含该 OOB 挂载点**。否则，SPA 导航由于不经过全页渲染，无法触发非 OOB 区域的清理，会导致旧页面的组件“泄露”到新页面中，引发严重的 ID 冲突和事件监听积压。

2. **CSS 权重压制**：为了修遮罩残留将 CSS 设为了 `display: flex !important`，结果导致 Alpine 变量设为 `false` 后依然被 CSS 强行显示；或者设为了 `display: none !important` 导致点击按钮后弹窗死活不出。
3. **缺失默认隐藏**：部分 Toast 在 CSS 中没有设置 `display: none`，导致在 JS 加载前的微秒级空隙内以“裸奔”状态显现。

### 修复方案 (V3.2.4)

1. **撤销手动扫描**：移除 `base.html` 中的冗余 `Alpine.initTree` 调用，完全依靠 Alpine 3 的底层 `MutationObserver` 处理 DOM 刷新。
2. **CSS 静默策略**：所有 Overlay 和 Toast 默认 CSS 设置为 `display: none`，且不加 `!important`。
3. **类绑定强制激活**：引入 `.active { display: flex !important; }` 类，由 Alpine 变量动态绑定（`:class="{ 'active': showResetModal }" `）。
   - **原理**：Alpine 的动态类绑定具有最高优先级，能稳定战胜 CSS 默认静默逻辑，确保“点开必现，关必消失”。

### 验证结果
- 多页面疯狂切换测试：✅ UI 零残留，弹窗响应毫秒级复归。

## 修复记录 #017-V3 — 仪表盘跳转 URL 推送与侧边栏状态彻底解决 (Final Patch V3.2.11)

### 问题描述

### 根本原因
1. **htmx.ajax 局限性**：JS 编程式调用的 `htmx.ajax` 在部分配置下不会自动触发 URL 更新。
2. **语义缺失**：原本使用 `div` 承载点击，缺乏 <a> 标签的天然导航特性。

### 修复方案 (V3.2.11 终极闭环)
1. **语义化重构**：将异常列表项改为 `<a>` 标签并内嵌 `hx-` 属性，增强跳转信号。
2. **后端强制推送 (`views.py`)**：只要目标是 `main-content` 区域，后端通过 `HX-Push-Url` 标头直接强制浏览器更新地址栏，不依赖前端参数。
3. **历史事件联动 (`base.html`)**：监听 `htmx:pushedIntoHistory` 确保侧边栏高亮在 URL 变动的一瞬间即完成同步。
