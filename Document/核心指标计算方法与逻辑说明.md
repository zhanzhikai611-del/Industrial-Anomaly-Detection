# V3.3.6 核心指标计算方法与逻辑说明

本文档旨在详细阐述「CNC 智能预警系统」中仪表盘、生产计划达成看板、以及事件中心/设备矩阵等核心数据指标的具体计算逻辑与理论模型。

---

## 1. 仪表盘：综合效能指标（OEE）及子指标计算

系统会在 **仪表盘** 的 `/api/stats/` 接口中实时聚合计算全局的 OEE（设备综合效率）表现。全局 OEE 是由全厂设备的 **A（可用性）**、**P（表现度）** 和 **Q（良率）** 严格连乘所得。

### 1.1 可用性 (Availability, A) —— 「时间加权移动平均法」 (V3.3.1 升级)
*   **逻辑**：反映设备开机运行时间的比例。
*   **计算方法**：
    1. 抓取全厂最近 **600 条记录** 的环形窗口样本。
    2. 对样本内每一条记录的 `loading_time`（计划生产时长）与 `downtime`（故障/待机时长）进行求和。
    3. **公式**：`A = (Σ loading_time - Σ downtime) / Σ loading_time`
*   **改进点**：告别了旧版本的“瞬时瞬间快照”，新的算法具备 **「故障记忆」**。哪怕设备只是坏了 3 秒钟，在接下来的窗口周期内 A 指标都会由于 3 秒的损失而产生跌降，使看板能够清晰捕捉到那些被肉眼忽略的小型故障。

### 1.2 表现度 (Performance, P) —— 「流水潜力对齐逻辑」 (V3.3.1 终极版)
*   **逻辑**：反映运行期间的实际产出速率与理论标准的偏差。
*   **计算方法**：
    1. 同样截取最近的 **600 条记录**。
    2. **潜力求和**：遍历每一条记录，分母根据该设备的 `standard_capacity` 和该记录代表的 `loading_time` 实时算出「该时刻应有的理论产量」。
    3. **公式**：`P = (Σ 实际产出件数) / (Σ 理论应产件数)`
*   **改进点**：该算法彻底解决了 V3.3.0 之前的「采样边界偏差 (Sampling Bias)」。由于分子(实际件数)与分母(对应时长的能力)在每条记录级别实现了 **1:1 物理对齐**，它不再受采样频率抖动、系统负荷带来的延迟影响，数值极其精准且稳定，告别了莫名其妙卡在 100% 或虚高的问题。
### 1.3 良率 (Quality, Q) —— 「物理实测逻辑」
*   **逻辑**：反映符合质量检测标准的产品数量占比。
*   **计算逻辑**（V2.1.2 升级）：直接引用全厂今日累计产出的良品数与投入总数的比例。这得益于脉冲仿真引擎（V5）提供的精确计数能力。
*   **公式**：`Q = (全厂良品总产量) / (全厂投入总数)`
*   **说明**：此算法摒弃了旧版本的 AI 风险系数估计法，利用真实的计件数据实现了财务级的数据闭环。

## 3. 事件中心/设备矩阵：单机实时效率 [表现度(P)] 与风险评估

### 3.1 实时风险 (Anomaly Score) 计算
采用 **逻辑回归 (Logistic Regression)** 模型进行 0-100% 概率预测。

### 3.2 单台设备的动态表现度 [P]（核心逻辑演进）

这是系统演进最频繁的部分。为了保证单机指标与全局指标的视觉一致性，系统经历了三代逻辑变革：

#### A. [当前运行] V3.3.6：1:1 物理对齐法 (Precision Alignment) —— 跨架构对齐
**设计目标**：彻底解决单机表现度 (P) 在 Redis 架构升级后可能出现的“响应过慢”与“边界跳变”问题。

*   **窗口定义**：观察该设备 **最近 30 分钟** 的物理流水记录。
*   **计算方法 (V3.3.6 核心突破)**：
    1.  **分母纯净化**：不再使用原始 `loading_time`（负荷时间），而是实时计算 `Actual_Run_Time = loading_time - downtime`（实际运转时间）。
    2.  **物理时长求和**：汇总该窗口内所有记录的实际运转时间之和，作为分母基准 $T_{run}$。
    3.  **计算公式**：$P = \sum(\text{实际投入件数}) / (Standard\_Cap \times T_{run})$。
*   **优点**：
    -   **瞬时响应**：彻底消除“停机惩罚同步”。当设备由停机恢复至运行（Down -> Running）后，分母将仅包含运行后的高效率片段，数值瞬间恢复，无任何拖尾爬坡。
    -   **逻辑闭环**：单机 P 的算力模型与全局看板 P 的模型完全同构，实现了全厂数据的单一事实来源 (Single Source of Truth)。

---

#### B. [对比] V3.3.1：滚动窗口瞬时法 (Sliding Window Snap) —— 墙上时钟版
**状态：已废弃 (作为过渡方案存档)**
*   **公式**：$\Delta T = \min(30min, \text{样本真实物理时间})$。
*   **缺陷**：采用的是 `now() - timestamp` 的时轴逻辑。在 Redis 缓存重启或模拟流不稳定的情况下，$\Delta T$ 包含大量未生产的空白期，导致 P 值严重缩水。

---

#### C. [对比] V2.1.1：时间轴差值法 (Wall-Clock Logic / Cumulative) —— 累计平均
**状态：已废弃 (作为每日成绩单存档)**

*   **逻辑**：从“今日第一条数据”一直累加到“现在”。
*   **公式**：`P = 今日总产出 / (产能 × (现在 - 开机时间))`。
*   **局限**：
    -   **“历史包袱”太重**：如果上午设备停机 4 小时，即使下午全力运转，P 值在很长一段时间内都会处于极低水平。
    -   **对调试不友好**：在频繁重置数据分布进行测试时，无法实时观察到“回春”后的数值提升。

---

#### D. [历史] V1.4.3：负荷时间累加法 (Area Sum Logic) —— 条数驱动
**状态：已淘汰**

*   **缺陷**：通过 `loading_time` 字段求和得出分母。在采样率变动（如 3 秒一条）时，如果不更新 `loading_time` 权重，会导致表现度 (P) 溢出或虚高，完全失去监测意义。

---

### 3.3 补偿机制：分层保护锁
为了防止系统启动或极端采样频率下的分母溢出，系统维持以下保护：
*   **全局看板**：保留 **30 秒 最小时长底线**。采用 600 条跨设备混抽样本。
*   **单机矩阵 (V3.3.6 优化)**：由于采用了 1:1 物理对齐法，分母自动跟随记录步长（如 3s）。系统不再设强制 5 分钟门槛，而是采用 **「记录存在性检查」**：只有当窗口内存在有效物理负载记录（LoadingTime > 0）时才进行计算，否则 P 展示为 0.0% 或保持最新缓存值。

## 4. Redis 架构下的数据同步规则 (V3.3.6 增补)
随着 V3.3.0 Redis 架构引入，数据流转遵循“分层治理”原则：
1.  **瞬时状态 (Live Snapshot)**：主轴电流、功率、当前工序、AI 预警分数直接存取于 Redis `device:status:all`。
2.  **效能指标 (OEE/P)**：
    -   **实时展示层**：前端设备矩阵优先读取由 `run_realtime_stream` 计算并推送到 Redis 的**瞬时 OEE (EMA 权重值)**。
    -   **数据校验层**：当用户刷新页面或进入详情页时，系统自动切换至 **DB 30分钟滑动窗口物理聚合**，实现对 Redis 缓存数据的定期校准与“脱水”。
3.  **产量基准**：今日累计产量 (`total_output`) 以 Redis 原子计数器为准，作为 Q（良率）计算的唯一算力来源。

## 5. 员工手册：OEE 常识与操作指南 (SOP)

为了让一线操作员更好地与 Agent 协同工作，以下是关于 OEE 指标及其背后逻辑的通俗解释。

### 5.1 OEE：衡量你工作效率的“金标准”
作为现代化工厂的一员，你不仅要“修好机器”，更要“运行好机器”。系统通过 **OEE (Overall Equipment Effectiveness，全局设备效率)** 来评估生产表现。

#### **OEE 的计算公式**
系统采用严格的连乘逻辑：
$$OEE = A \times P \times Q$$

1.  **可用性 (Availability, A)**：
    - **意义**：机器有多少时间在干活。
    - **计算**：$(\text{计划时长} - \text{停机时长}) / \text{计划时长}$。
    - **提升技巧**：减少找工具、调机、闲聊导致的非计划停机。
2.  **表现度 (Performance, P)**：
    - **意义**：干活的速度快不快。
    - **计算**：$\text{实际产出} / (\text{标准产能} \times \text{实际运转时间})$。
    - **注意事项**：系统采用 1:1 物理对齐法，这意味着如果你为了偷懒而调低机器倍率，P 值会立即下跌。
3.  **良率 (Quality, Q)**：
    - **意义**：干的活有多少是合格的。
    - **计算**：$\text{良品总数} / \text{投入总数}$。
    - **技术支撑**：系统通过 `yield_buffer` 脉冲累加器精准统计每一件产出，确保数据真实不可篡改。

#### **实际意义：为什么要看 OEE？**
- **暴露“隐藏的工厂”**：OEE 能够捕捉到那些仅持续几秒钟的小停机。
- **成本闭环**：老化设备（如样本中的故障组）虽然还在运行，但如果 Q 值（良率）因磨损导致持续走低，OEE 就会提醒管理层：**换新机的成本可能低于报废工件的成本**。

## 6. 常见问题 (FAQ)

- **Q：为什么看板上的产量突然暴涨？**
  - **A**：这通常是 `yield_buffer` 逻辑失效的表现。请联系技术员检查 `run_realtime_stream.py` 进程，确保产能碎片按约 0.05 分钟的份额正确累加。

- **Q：为什么 AI 报警了，但机器看起来没问题？**
  - **A**：AI 具备“预见性”。它可能检测到了主轴功率微小的非线性波动（`interaction_current_x_power`），这是刀具即将崩刃的前兆。请参考“双轴联动图”进行交叉验证。
