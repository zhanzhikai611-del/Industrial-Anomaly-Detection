### 一、 Copilot 核心运行逻辑（閉環流程）

![image-20260306122423049](/Users/chanchihkai/Documents/基于机器学习的工业生产数据异常预警系统/Document/assets/image-20260306122423049.png)

Agent 开启后，将按照以下逻辑在后台循环执行，并将每一步的执行结果实时推送到中间的**虚拟终端**中：

1. **全局扫描 (Global Scan)**：
   - **逻辑**：每隔 10 秒扫描 `device_info` 表，寻找 `current_risk_score`（实时风险）最高的设备。
   - **终端输出**：`[System] 正在扫描全线 25 台设备风险状态...`
2. **锁定目标 (Lock Target)**：
   - **逻辑**：发现风险值超过75%预设阈值的设备。
   - **终端输出**：`[Target] 锁定高风险设备：Punch-冲压-05，风险值：93.8%`
3. **安全停机 (Safety Shutdown)**：
   - **逻辑**：下发指令将该设备的 `current_status` 修改为 `Stopped`。
   - **终端输出**：`[Action] 已触发紧急停机指令，设备状态 -> Stopped`
4. **数据采集 (Data Harvesting)**：
   - **逻辑**：读取该设备最近 10 条 `anomaly_alert_log`（报警日志）。
   - **终端输出**：`[Info] 成功提取 10 条异常上下文快照（主轴电流/功率异常）...`
5. **AI 诊断 (AI Diagnosis)**：
   - **逻辑**：将数据打包发送至 LLM，获取针对性维修意见。
   - **终端输出**：`[AI] 正在通过 LLM 进行多维关联分析... 诊断意见：建议检查刀具磨损情况。`
6. **触发性能回春(Recovery)：**
   * 将 `device_info.current_group_id` 重置为 `1`（模拟更换新刀具）
7. **指令下发与复位 (Reset)**：
   - **逻辑**：将诊断结果写入系统日志，并将设备 `current_status` 恢复为 `Running`。
   - **终端输出**：`[System] 诊断建议已下发至维修单，设备恢复运行。`

### 二、 “模式接管”的技术实现方案

![image-20260306122453784](/Users/chanchihkai/Documents/基于机器学习的工业生产数据异常预警系统/Document/assets/image-20260306122453784.png)

为了实现“开启后不允许操控，点击退出恢复”的效果，你需要从**前端阻断**和**后端通信**两个维度入手：

#### 1. 前端：全局交互阻断 (The "Glass Wall")

- **实现方式**：在 `Copilot` 模式开启时，在所有页面组件上方覆盖一个全屏的透明层（Overlay）。
- **CSS 核心属性**：
  - 设置 `pointer-events: none;` 给下方的仪表盘内容，防止点击。
  - 设置 `backdrop-filter: blur(8px) brightness(0.6);` 实现你设想的磨砂暗化效果。
- **呼吸灯边框**：使用 `box-shadow` 的内发光效果，配合 `keyframes` 动画实现蓝色渐层的呼吸感。

#### 2. 通信：实时日志推送 (WebSocket)

- **实现方式**：使用 **Django Channels (WebSocket)**。
- **逻辑**：
  - 当 Agent 每完成一个步骤，后端会向前端推送一条 JSON 消息。
  - 前端 JavaScript 监听到消息后，实时将文本追加到中间“虚拟终端”的列表中。

### 三、 Copilot 模式可行性分析与资源清单

#### 1. 可行性分析 (Feasibility Analysis)

当前系统架构（Django +原生 JS/ECharts）完全具备实现该 Copilot 模式的条件，整体可行性**极高**，具体的落地评估如下：

- **后台 Agent 循环与数据流转 (Scan & Action)**：
  - **当前状态**：已有完善的 Django ORM，且存在现成的状态字段 `current_status` ('Running'/'Down') 以及换刀模拟字段 `current_group_id`。设备的数据停机与回春均可通过直接修改这几个字段实现。
  - **调整点**：目前 `device_info` 中无 `current_risk_score`（实时风险分来源于 `anomaly_alert_log`）。只需写一个后台任务（使用 `asyncio` 或 `Threading` 配合 Django 环境）定时连表查询出最高风险设备即可锁定目标。
- **前端全局阻断 (Glass Wall)**：
  - **当前状态**：前端原生标准开发。
  - **调整点**：通过 CSS 的 `pointer-events: none` 和 `backdrop-filter` 实现全局接管，没有任何兼容性问题，易于落地。
- **AI 诊断整合 (LLM Integration)**：
  - **当前状态**：后端为原生 Python，非常契合目前主流的大语言模型生态环境。把 `anomaly_alert_log` 中的多维时序传感器数据拼成 prompt 毫无难度。
- **实时日志通信 (WebSocket 终端推送)**：
  - **当前状态**：系统当前可能是典型的 WSGI 架构，依赖 HTTP 定时轮询更新（例如 dashboard.html 中的 setInterval）。
  - **调整点**：需要将 Django 升级为 ASGI 模式，引入 `Django Channels` 来推送 Agent 执行到具体哪一步的状态，以此驱动前端的“虚拟终端”逐行打印。

#### 2. 研发所需资源清单 (Resource Checklist)

在正式启动开发代码之前，需准备以下外部资源和系统环境更新：

1. **大模型 API Key（LLM API Key）**
   - 需提供大模型的 API 调用凭证，如 OpenAI 的 `sk-...` 密钥，或国内推理强大的平台（如 通义千问 / DeepSeek / Kimi 等）皆可。
   - Qwen 密钥 `sk-6244491a10cd439b9d9013b557450741` 
2. **WebSocket 组件环境包（Python）**
   - 需在 `requirements.txt` 补充安装 `channels`、`daphne` 库以支持异步 WebSocket 推送。
   - 消息层中间件（可选）：若是供本机简单演示，可以使用 `channels` 的 `InMemoryChannelLayer`；若需要更稳定或多进程环境，则建议本地安装 **Redis 集群**并配合 `channels-redis` 库。
   - 先实现本地展示即可
3. **LLM 接口请求包**
   - 如果使用通用大模型 API，可以直接使用第三方包如 `openai`, `dashscope`；或者使用原生的 `requests` 等 HTTP 库自己构造请求体发送。
