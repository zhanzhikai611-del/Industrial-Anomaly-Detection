### V2.1.1 产品需求文档

本版本核心目标是增强系统对仿真数据的动态控制能力，在“系统设置”页面引入全局化的设备风险重置机制。

------

#### 1. 数据设置模块优化 (Data Management)

**视觉变更**：
- 将原“**实时数据流控制**”卡片标题更名为“**数据设置**”。
- 移除了卡片底部的文字说明（“控制后台守护进程向数据库写入仿真传感器数据...”）。
- 新增“**重置设备风险分布**”交互入口。

**功能定义**：
在“数据设置”卡片内，数据流状态开关下方，新增 [立即重置] 按钮。

**业务逻辑**：
- **触发对象**：全量 25 台设备。
- **重置规则**（按设备物理 ID 映射）：
  - 设备 ID [1-5]   → 重置为 **Group 1** (新设备，AI 风险 0-40%)
  - 设备 ID [6-11]  → 重置为 **Group 2** (准新设备，AI 风险 30-50%)
  - 设备 ID [12-18] → 重置为 **Group 3** (正常设备，AI 风险 41-75%)
  - 设备 ID [19-23] → 重置为 **Group 4** (老旧设备，AI 风险 60-85%)
  - 设备 ID [24-25] → 重置为 **Group 5** (故障边缘，AI 风险 76-100%)
- **实时响应**：重置完成后，后台 `run_realtime_stream.py` 守护进程将在下一个心跳周期（≤3秒）内感知 `current_group_id` 的变化，并立即按新组别参数生成仿真数据。

**技术实现点**：
- **后端 API**：已实现 `POST /api/system/reset_groups/` 接口。
- **前端交互**：
    - 按钮采用红色警示风格（`background: #f56c6c`），与数据流开关错位排列。
    - 点击时触发 JavaScript `confirm` 弹窗。
    - 执行成功后弹出完成提示。

#### 2. 核心指标算法优化 (OEE Algorithm Refinement)

**背景问题**：
V2.1.0 版本中由于仿真步长从 1 分钟缩短至 3 秒，单机 OEE 计算逻辑仍采用旧有的 `loading_time` 累加法，导致分母严重偏小，全量设备 OEE 异常偏高（接近 100%），无法真实反映设备闲置状态。

**优化方案**：
- **算法切换**：由「数据切片累加法」切换为「**时间轴差值法 (Wall-Clock Logic)**」。
- **计算逻辑**：
  - 锚定今日第一条数据的时间戳作为生产起点。
  - 以系统当前时间作为终点计算绝对耗时。
  - 理论产量分母 = `标准产能 × (当前时间 - 首条数据时间)`。
- **预期效果**：不论数据上传频率如何，只要设备在物理时间内没有产出，OEE 分数将忠实地下滑，从而能够准确监测数据流暂停或设备闲置的情况。

#### 3. 可行性评估总结

| 评估项 | 结论 | 理由 |
| :--- | :--- | :--- |
| **技术可行性** | 🟢 极高 | 项目已有 `_get_group_id` 映射逻辑及单设备重置 API，复用逻辑成本极低。 |
