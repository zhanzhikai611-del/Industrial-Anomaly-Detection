# 工业生产数据异常预警系统 —— 数据库模型与逻辑计算 (V3.5.0)

## 1. 核心数据模型实现 (`monitor/models.py`)

### 1.1 `DeviceInfo` (设备核心资产)
管理车间物理资产的静态与动态状态。
*   **重置函数 `initial_repair_all()`**:
    *   *实现*: 使用 `transaction.atomic()` 开启原子事务。
    *   *逻辑*: 遍历 25 台设备，根据索引分配初始损耗梯度（G1-G5），并批量执行 `bulk_update`。
    *   *用途*: 用于系统启动自检或管理员一键恢复实验环境。
*   **字段 `maintenance_advice`**: 
    *   *实现*: `models.TextField`。
    *   *逻辑*: 这是一个“活字段”，由 AI Agent 生成诊断建议后通过 `update(maintenance_advice=advice)` 写入。

### 1.2 `ProductionSensorData` (高频流水与指标计算)
这是系统中数据量最大的表，承载了所有 OEE 指标的底层计算逻辑。
*   **OEE 动态计算属性 (@property)**:
    *   **`availability` (时间稼动率)**: 
        ```python
        return (self.loading_time - self.downtime) / self.loading_time
        ```
    *   **`performance` (性能稼动率)**: 
        计算公式：`实际产量 / (实际运转时间 * 标准产能)`。其中实际运转时间通过 `(loading_time - downtime) / 60` 换算为小时。
    *   **`quality` (质量合格率)**: 
        计算公式：`actual_output / input_qty`。
    *   **`oee`**: 综合上述三个 Property 的乘积。
*   **索引优化**: 
    *   定义了 `models.Index(fields=['device', 'timestamp'])`，确保大屏查询单台设备历史曲线时能在毫秒级定位数据。
    *   对 `anomaly_score` 建立索引，支撑“按风险值排序”的高频查询。

### 1.3 `SystemConfig` (单例配置中枢)
确保全系统只有一套控制参数。
*   **单例实现**: 重写 `save()` 方法。
    ```python
    def save(self, *args, **kwargs):
        self.pk = 1  # 强制主键始终为 1
        super().save(*args, **kwargs)
    ```
*   **获取方法 `get()`**: 使用 `cls.objects.get_or_create(pk=1)`，确保任何时刻调用都能拿到合法的配置实例。

## 2. 缓存架构逻辑实现 (`services/cache_service.py`)

为了弥补 MySQL 在高频读取下的性能短板，系统引入了 Redis 缓存层。

### 2.1 实时快照引擎 (`update_device_snapshot`)
*   **存储结构**: Redis Hash。Key 格式为 `device:snapshot:{id}`。
*   **更新逻辑**: 由后台仿真引擎在生成数据时顺带触发，将主轴电流、功率、当前风险分写入 Redis。
*   **读取逻辑**: `stats_service.get_device_matrix_data` 会优先扫描 Redis。如果 Redis 命中，则跳过 MySQL 查询，直接将快照组装为 JSON 返回前端。

### 2.2 产量原子计数器 (`incr_daily_output`)
*   **实现**: 使用 Redis 的 `INCRBY` 原子操作。
*   **逻辑**: 当仿真引擎产生 `produced` 件数时，调用该函数更新 `stats:output:today`。
*   **持久化同步**: 定时任务会对比 Redis 与 MySQL 的产量差异，确保数据一致性。

## 4. 高级存储架构设计 (V3.5.0 专项)

### 4.1 双层存储优化 (Hybrid Storage Strategy)
系统采用了“热-温-冷”三级存储模型：
*   **热数据 (Redis)**：存储 25 台设备的实时快照（Snapshot）与今日产量计数器。读写延迟控制在 5ms 以内，支撑前端 3s 一次的无感知刷新。
*   **温数据 (MySQL - InnoDB)**：存储最近 24 小时的全量传感流水与报警日志。通过索引优化，支撑详情页时序图表的毫秒级回溯。
*   **冷数据 (MySQL - Archive)**：超过 24 小时的数据会被滚动清理或归档，确保数据库 B+ 树索引层数维持在较低水平，保障查询性能不随时间线性衰减。

### 4.2 索引与查询性能优化
*   **复合索引设计**：在 `ProductionSensorData` 表上建立 `(device_id, timestamp DESC)` 复合索引。这使得“获取某设备最新 N 条记录”的操作直接命中索引叶子节点，无需全表扫描。
*   **覆盖索引应用**：在看板统计查询中，通过只选择 `anomaly_score` 字段，实现了索引覆盖查询（Index-Only Scan），极大地降低了磁盘 I/O。

### 4.3 检索增强 (RAG) 向量库集成
*   **非关系型扩展**：系统通过 `FAISS` 实现了本地向量存储。
*   **映射机制**：通过 `knowledge_service` 建立向量 ID 与本地 Markdown 文件路径的映射。当 Agent 检索到相关片段时，后端通过路径直接读取物理文件，实现了“结构化模型数据”与“非结构化文档知识”的跨维度关联。
