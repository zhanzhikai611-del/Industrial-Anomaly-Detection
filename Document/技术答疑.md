# 技术答疑

## Q1: 为什么一开始用 `manage.py runserver`，后面启动命令改成了 `daphne -p 8000 IndustrialWarningSystem.asgi:application`？

**一句话总结：**
因为 V2.0 引入了 Copilot 智能体，它的实时终端功能需要用到 **WebSocket 长连接** 技术，而传统的 `runserver` 环境主要是为了处理普通的 HTTP 短连接（WSGI）而设计的，无法完美支持我们的实时通道，所以需要更换为支持异步框架（ASGI）的 `Daphne` 服务器。

**详细解析：**

1. **WSGI vs ASGI：协议的差别**
   - **WSGI (Web Server Gateway Interface)：** 这就是您之前使用 `python manage.py runserver` 时 Django 默认启动的模式。它的特点是“一问一答、用完即走”：浏览器发送一个请求（比如拿一下统计数据），服务器处理完返回结果，连接就断开了。它是一个**同步阻塞**的模型。
   - **ASGI (Asynchronous Server Gateway Interface)：** 由于我们的 Copilot 智能体需要将它在后台每几秒钟执行的检查情况、大模型的诊断结果一条条**主动推送**给前端显示出来，所以我们需要建立一个“打不挂的电话通道”，这就是 WebSocket。ASGI 协议就是专门为处理这类异步长连接、WebSocket、后台持续轮询广播而发明的。

2. **什么是 Daphne？**
   - Daphne 并不是凭空出现的神秘软件，它是 **Django Channels**（Django官方提供的处理 WebSockets 扩展库）团队开发的一款标准 ASGI 服务器。
   - 当我们使用 `daphne -p 8000 IndustrialWarningSystem.asgi:application` 这个命令时，实际上是在启动一个能够同时监听 HTTP 网页请求和 WebSocket 实时请求的外壳，它会替代原本单一的 Django 开发服务器。

3. **系统的底层路由分流 (`asgi.py`)** 
   我们并没有抛弃以前写的普通 HTTP 代码，我们修改了底层的入口 `asgi.py`。这就像是在大门口装了一个智能分拣机（`ProtocolTypeRouter`）：
   - 当浏览器只是普通访问“仪表盘主页、设备监控”页面（`http://`），分拣机会把流量抛给旧的 Django (WSGI) 视图函数，原样输出。
   - 当我们在浏览器中按下了 "Copilot 按钮"，前端会发起一条 `ws://` 打头的 WebSocket 握手请求。分拣机识别到后，就会把信道分配给我们新开发的 `CopilotConsumer` (在 `consumers.py` 里)，建立起持续通信的绿色通道。

> **小贴士 (Tips)：**
> 只有使用了 Daphne 这类 ASGI 引擎，您看到的 Copilot 终端界面上的“日志逐字冒出”效果才能做到丝滑不卡顿。普通的 `runserver` 面对这种长连接容易把所有工作线程全部卡死。
