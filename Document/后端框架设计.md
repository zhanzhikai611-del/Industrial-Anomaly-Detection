# 后端架构设计与演进方案 (V2.2.1+)

## 1. 现状：基于“大屏+孪生+AI”的智能协同架构 (当前阶段)

当前系统的后端架构已突破了传统的 Django MTV 范式，演进为涵盖 **RESTful API 数据流**、**WebSocket 实时全双工通信**以及 **在环 AI 模型推断** 的复合型工业互联中枢。

### 1.1 核心架构模式：业务解耦与双栈驱动
*   **同步栈 (WSGI/Views)**：负责传统的页面路由分发、权限控制 (RBAC) 以及 RESTful 接口的数据聚合。所有的 CRUD 操作和统计分析（如当天的 OEE 计算、报警趋势等）均通过同步 API 处理。
*   **异步栈 (ASGI/Channels)**：引入 Django Channels 应对高频实时的工业数据推送。通过 `consumers.py` 实现了服务器主动向浏览器广播状态，彻底告别了传统 HTTP 长轮询的性能瓶颈。
*   **AI 内聚逻辑**：后端的 AI 能力分为两层：
    1.  **判定层 (边缘监督学习)**：利用 `joblib` 在内存中常驻的轻量级逻辑回归 (LR) 模型，对流式传感器数据进行毫秒级的刀具磨损风险预测 (`anomaly_score`)。
    2.  **诊断层 (云端大语言模型)**：引入 OpenAI 接口，挂载 RAG 特性，能够读取上下文后生成维修维护建议。

## 2. 核心模块与文件拓扑深度解析

后端代码完全遵循高内聚、低耦合的设计原则。所有的主要业务逻辑都被拆解到了特定的职责域中。

### 2.1 物理数据层：`models.py` (工业资产与流水的映射)
数据库设计摆脱了简单的 CRUD 束缚，而是高度契合了**工业设备的实际运行逻辑**。
*   **`DeviceInfo` (资产维)**：定义车间机床的稳态元数据，提供 OEE 计算的理论最大产能（`standard_capacity`）以及当前的物理运行状态。
*   **`ProductionSensorData` (流水维/特征维)**：最为庞大的核心业务表。不仅融合了 CNC 数据集（主轴电流、主轴功率、进给速度），还承担着 OEE 指标模型（负荷时间、停机时间、产出）的持久化。
    *   *高级特性*: 不将 `oee`、`performance` 等作为物理字段落库，而是采用 Python `@property` 只读属性在运行期实时（或划定时间窗口）推断，确保数据无延迟和规避冗余。
*   **`AnomalyAlertLog` (警报维)**：追踪并留存高危异常的发生与处理生命周期。
*   **`SystemConfig` & `SystemLog`**：单例全局控权机制与进程间解耦的通信信使。

### 2.2 同步计算层：`views.py` (数据聚合与控制接口)
该模块是所有 Http API 请求的首要中转站，代码虽然庞大，但主要承担以下三类任务：
1.  **全景数据聚合 (`api_dashboard_stats`)**：负责运用复杂的基于时间的聚合函数查询 (`TruncHour`, `Sum`)，对 8 小时的产量进行滑动窗口计算，输出可直接用于 ECharts 渲染的阵列数据。
2.  **LR 模型在线批处理 (`api_device_matrix`)**：在为前端组装设备列表时，顺带提取每台设备的最后一帧数据喂给全局单例的特征缩放器 (`_SCALER`) 和 `_LR_MODEL` 模型，同步计算出风险概率。
3.  **鉴权拦截 (`@role_required`)**：通过自定义装饰器拦截非法越权操作，结合系统的 RBAC 进行前端访问控制。

### 2.3 异步总线层：`consumers.py` (实时指挥中心)
它是整个系统中最具活力的模块，承担着“心脏泵血”和“自动驾驶”的作用。
*   **`FactoryConsumer`**：每 3 秒构建一次 25 台设备的实时物理特征快照与计算 OEE，通过 Websocket 向前端数字孪生大屏 (`factory.html`) 穿透下发，保证了 3D 前端无缝动画。
*   **`CopilotConsumer`**：内置了完整的**大语言模型后台自循环 (Autonomous Agent)** 机制。
    1.  主动轮询 `get_highest_risk_device()` 寻找高危待宕机设备。
    2.  调用 `get_harvest_data()` 获取停机前的异常传感数据切片。
    3.  通过子网格抛给 `run_ai_diagnosis`，借由 Qwen 或 OpenAI LLM 获取排障说明。
    4.  调用 `perform_recovery` 全自动完成数据库标记与复位，形成高度闭环。

### 2.4 推理大脑层：`ai_engine.py` (Copilot / RAG 工具链)
核心的问答调度中心，使得系统的交互方式从“看仪表”升级到了“问助理”：
*   **Function Calling 工具挂载**：暴露 `get_device_recent_data` 接口，赋予 LLM 操作/读取系统数据库状态的能力。
*   **动态提示词与上下文**：使用 `ask_copilot_with_tools` 在云端 API 交互时组装精确的指令上下文，提取有效历史进行数据喂测，解决泛泛而谈的局限。

### 2.5 边缘判定层：模型在线预估机制
系统剥离了复杂的 AI 训练框架（如 TensorFlow/PyTorch），纯粹依靠 `scikit-learn` 与 `joblib`，在 Django 进程内进行毫秒级实时推理。
*   **模型单例常驻内存**：在应用启动时一次性加载 LR 推理模型 (`logistic_model.pkl`) 与特征缩放器 (`scaler.pkl`) 为全局单例，阻断后续预测的任何磁盘 I/O。
*   **实时特征向量组装**：通过核心包装器 `_predict_proba(record)`，从实时流水中提取 3 组物理量（主轴电流、主轴功率、进给速度），组装并归一化为匹配模型训练输入的 9 维特征矩阵，最后调用 `_LR_MODEL.predict_proba()` 输出异常概率。
*   **高频总线调度**：得益于极度轻量的内存短点运算，模型推理被直接挂载于 HTTP API (`views.py`) 与 WebSocket 心跳 (`consumers.py`)。在数字孪生大屏每 3 秒级别的刷新频率下，系统能同步完成全厂 25 台设备的并发推断，并通过 `anomaly_score` 触发前端红框报警与后台 Copilot 自动诊断。

## 3. 演进路线图：系统架构进一步梳理 (V3.0 展望)

随着前端体系迈入 `HTMX + Alpine.js` 的解耦阶段，后端同样需要从“巨石结构”中轻盈转身。

### 3.1 拆除重型 Views 
*   **分析**：目前的 `views.py` 中的 `api_dashboard_stats` 由于强耦合了所有的图表聚合计算，随着以后图表种类的扩展，将迅速达到无法维护的边缘。
*   **优化**：建立 `services/` 层，剥离纯数据组装逻辑。`views.py` 应当只负责接管 Http 参数和抛出 JSON 响应；所有类似于 OEE 计算的复杂 SQL 将重构进 `services/oee_calculator.py`。

### 3.2 独立化模型微服务
*   **分析**：现有的 `logic_model.pkl` 被单例硬编码在内存中，每次重新训练和部署都必须重启后端服务。
*   **优化**：预留接口建立轻量的模型独立服务（比如基于 FastAPI），通过 gRPC 或者内部 HTTP 请求与系统的核心代码分离，使训练和推理互不干扰。

### 3.3 提升队列通信性能
*   **分析**：现在借助的是 `SystemLog` 表在数据库中频繁产生 `engine_log` 以充当进程间通信（守护流进程向 Web 层的推送），在大规模集群中极为耗费数据库性能。
*   **优化**：准备引入 **Redis Channel 层**，全面替代数据库轮询机制，真正打通 Channels 之间的内存级广播总线。
